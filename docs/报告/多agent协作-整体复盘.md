## 0. 一页摘要

如果把这几天的东西压缩成五句话：

1. **按文件并行的多 agent 开发是可行的。** 3 个 agent 在同一目录、6 分钟，交付 485 行实现 + 856 行测试 + 195 行验收测试，83 个测试全绿，没有手工冲突。
2. **同一文件的并发写不是“小心一点”能解决的。** 进程级裸读改写丢了 62% 的更新；agent 级靠工具的快照校验只能把冲突变成报错；真正归零的是原子租约。
3. **通信能改善协调，但不能替代原子性。** 纯广播“我要写了”约等于没发；收到消息后退避能把丢失从 61% 压到 2.4%，但不归零；原子租约才归零。
4. **A2A 补的是“横向通信”，不是“共享工作区一致性”。** 两个 agent 可以跨进程互相调用，但文件锁、验收、治理仍然要自己建。
5. **任务分配是运筹学问题，组织设计是更高一层的双层问题。** 但“动态组织”不是默认答案：仿真里组织选择对目标权重大幅敏感，而动态重组的收益上限（oracle − best fixed）接近 0，甚至被探索成本吃掉。

一句话：**我们已经知道“怎么让多个 agent 不互相踩”的工程骨架；还没证明“动态组织”在真实项目里一定划算。**

## 1. 起点：朋友那份 Agent Guild 草案

那份文档提出了一个很清楚的产品：用户当“公会管理员”，手动把任务派遣给 Codex、DSH、Claude Code 等 agent；每个 agent 在独立 worktree 里干活；平台统一管资源锁、日志、交接、自动测试和人工验收。

它把问题定义对了，而且几个判断很准：

- Worktree 只是目录隔离，不是文件锁；
- 验收必须分“自动测试”和“人工验收”；
- 日志要“摘要 + 证据引用”，不能复制长 diff；
- 不同厂商的 agent 要统一到同一套任务/事件模型。

但它没有回答最硬的部分：**锁/租约的具体协议、跨 worktree 的合并门禁、以及“派遣”如何真正送达一个已经关闭的客户端。** 我们后面的实验，基本就是围绕这三件事展开的。

## 2. 实验一：三个 agent 在同一工作空间做一个项目

### 2.1 怎么做的

我们先写了一份冻结的 `CONTRACT.md`（函数签名、数据结构、错误语义），再写了 11 个黑盒验收用例，然后才让 3 个 agent 并行实现：

- `agent-storage`：`storage.py` + `test_storage.py`
- `agent-report`：`report.py` + `test_report.py`
- `agent-cli`：`cli.py` + `test_cli.py`
- 编排者：契约、验收、提交，不写实现

规则只有四条：契约先行、验收先行、文件所有权、agent 禁止 git 写操作。

### 2.2 结果

6 分钟，485 行实现、856 行测试、195 行验收测试，合计 1360 行新增。四套测试全绿：

```text
test_storage     17 tests
test_report      33 tests
test_cli         22 tests
test_acceptance  11 tests
```

`git diff --numstat` 只出现预期的 8 个文件，没有 agent 改到别人的文件；集成时没有手工冲突，也没有返工。

### 2.3 两个真实的坑

第一个坑是环境：本机 DSH 沙箱下，`tempfile.TemporaryDirectory` 创建的 0o700 目录不可写，两个 agent 各自踩了一遍，各自写了不同的绕行方案。**共享工作空间也共享环境缺陷；N 个 agent 会重复排查同一个坑。** 这类注意事项应该写进 README/契约，只踩一次。

第二个坑是“零集成返工”的真相：第一次跑验收时出现 7 个 failure + 1 个 error，全部是临时目录权限，不是实现问题。**环境噪声会伪装成集成失败；编排者要先排除环境，再判断代码。**

### 2.4 这条实验证明了什么

在“任务可切分、接口可冻结、验收可自动”的前提下，**按文件并行的多 agent 开发是工程上可行的**，而且不需要什么神奇框架：契约 + 所有权 + 验收 + git 审计就够了。

它没有证明的是：任务耦合度高、需要频繁讨论、或者多人同时改同一文件时，这套还成不成立。

## 3. 实验二：同一文件并发写，到底会怎样

### 3.1 进程级：裸读改写会静默丢更新

3 个进程对同一个 JSON 计数器各做 60 次「读 → 等 1ms → 整文件写回」，期望 180。结果：

| 轮次 | 实际 | 丢失 | 撕裂读 |
| --- | ---: | ---: | --- |
| 1 | 67 | 113 | 7/8/8 |
| 2 | 67 | 113 | 4/4/5 |
| 3 | 68 | 112 | 6/10/5 |

**所有进程退出码都是 0。** 没有报错、没有异常，62% 的更新就是没了。加上 mkdir 互斥锁后，三轮都是 180/180。

### 3.2 Agent 级：工具会拒绝过期快照

让 3 个 agent 同时读 `team.json`、等 6 秒、整文件覆盖写回自己的名字：

- 甲成功；
- 乙、丙被拒绝：`cannot write ...: file changed since it was read — re-read the file, then retry`。

最终只有甲的名字，**1/3 存活**。这不是静默丢失，而是显式拒绝——本会话的文件工具在写入前校验了“你读到的快照是否仍是当前内容”。

第二轮改成「遇到冲突就重读、合并、重试」：丁 0 次重试、戊 1 次、己 2 次，最终 3/3 全部写入。

### 3.3 这条实验证明了什么

- **工具路径受保护，shell 路径裸奔。** 用 `write`/`edit` 有快照校验；用 PowerShell/Python 直接写就退回静默丢更新。
- **保护不等于正确。** 拒绝过期写保证“不覆盖别人”，但要保证“不丢自己”，必须重读 + 合并 + 重试。
- **原子性必须在写入那一刻。** “读版本 → 复查 → 写”不是原子 CAS；两个 agent 可以同时通过复查，然后都写。

## 4. 实验三：A2A 能不能补上 agent 间的通信

上一轮发现：同级 subagent 不能直接发消息，会报 `belongs to another parent session`；文件系统是唯一共享黑板。A2A 正好补这个缺口。

我们用官方 `a2a-sdk 1.3.0`（A2A v1.0）起了两个 server：

- **Ledger Agent**（:8765）：记账；
- **Audit Agent**（:8766）：收到审计任务后，**自己作为 A2A 客户端**去调 Ledger Agent 取报表，再核对。

客户端只调了 Audit 一次，但发生了两跳：`client → audit → ledger`。`audit.ok = True`，三项检查全过，**audit → ledger 这一跳没有任何中心编排者参与**。失败路径也验证了：未知 action → Task 状态 `failed`，错误消息通过协议回传。

### 4.1 它解决了什么

- 同级 agent 直连；
- 标准发现（Agent Card）；
- Task 生命周期、artifact、流式、取消；
- 跨进程/跨厂商/跨语言。

### 4.2 它没解决什么

- 文件锁、租约、工作区一致性；
- 统一调度、预算、权限策略；
- 单机同进程父子委派（起端口 + 序列化，比原生 subagent 重）。

### 4.3 接入 DSH 的三条路径

1. **旁路服务化**（本次做法）：每个 agent 独立进程 + A2A server，DSH 侧当 client。
2. **Sidecar 桥接**：对外 A2A server，内部转成 DSH 会话；DSH 目前没有原生 A2A endpoint，要自己写网关。
3. **只在跨边界时用**：同工作区继续原生 subagent，A2A 只接外部黑盒 agent。

## 5. 实验四：通信、共享信息，到底能不能解决“打架”

这是你后来问的核心问题。我们把它拆成“通信”和“原子性”两个变量，跑了 6 种协议、每种 5 轮：

| 协议 | 通信 | 收到信息后行动 | 丢失率 |
| --- | --- | --- | ---: |
| `silent` | ❌ | — | 61.1% |
| `paced`（同节奏对照） | ❌ | — | 52.4% |
| `announce` 广播意图 | ✅ | ❌ 不避让 | 52.2% |
| `polite` 广播 + 退避 | ✅ | ✅ | 2.4% |
| `lease` 申请/授予锁 | ✅ | ✅ 持锁才写 | 0% |
| 读版本→复查→写 | ❌ | — | 38.4% |

四个发现：

1. **纯信息共享 ≈ 没有共享。** `announce` 52.2%，`paced` 52.4%，几乎一样。广播“我要写了”本身不产生协调效果；之前 `announce` 比 `silent` 好看，几乎全是“多等了 20ms”的错峰。
2. **信息 + 行动，能大幅改善，但不能归零。** `polite` 把丢失压到 2.4%，但 5 轮里仍有 4 轮丢 2–4 次。信息永远过期：两个 agent 可以同时看到“没人要写”，然后同时写。
3. **通信 + 原子租约，才归零。** `lease` 90/90，而且比退避重试更快（0.38s vs 2.44s）——排队比碰撞+重试便宜。工程上还要配 fencing token，防止租约过期后出现两个持有者。
4. **“先检查再写”不是原子操作。** 读版本 → 复查 → 写仍丢 38.4%；原子性必须在写入那一刻完成。

一个 2×2 就能概括：

| | 无原子性 | 有原子性 |
| --- | --- | --- |
| **无通信** | 61% 丢失 | 本地锁 / 事务：0 丢失 |
| **有通信** | 广播 52%；退避 2.4% | 租约：0 丢失 |

**决定“会不会丢”的是原子性；通信决定的是协调成本和语义质量。**

## 6. 设计一：协调插件 + 运筹学

你问“能不能做成一个协调多 agent 的插件，用运筹学做任务拆分，在多指标下求最优”。答案是能，但要把两个词拆开：

- **插件**：不是一个 UI 插件，而是**协调服务 + 薄适配层**。协调需要跨进程状态、原子租约、全局视图、后台重规划，这些都不是 UI 插件擅长的。
- **最优**：LLM 的工时/质量/token 都是估计值，不存在静态全局最优；实际能做的是**约束下的 Pareto 最优 + 滚动重规划**。

### 6.1 运筹学接在哪

- 任务拆分：WBS、DSM、依赖图划分/社区检测；
- 谁来做：广义分配、匈牙利算法、最小费用流、拍卖；
- 什么时候做：CPM/PERT、RCPSP、DAG 列表调度；
- 多目标：Pareto、ε-约束、加权和、AHP/SWING；
- 不确定性：随机规划、鲁棒优化、CVaR、bandit；
- 上下文/预算：背包问题；
- 吞吐/瓶颈：排队论、Little's Law、TOC；
- 质量：统计过程控制、验收抽样、质量成本。

### 6.2 数学形式

```text
min  Σ cost[i,j,m] · x[i,j,m]
s.t. 每个任务一个执行者、依赖、容量、上下文窗口
     P(quality ≥ q0) ≥ 1-α
     makespan ≤ D
     Σ cplx[i,j,m] · x ≤ C_budget     # 过度设计预算
```

多目标时用 ε-约束求 Pareto 前沿，让用户在前沿上选，而不是偷偷定权重。

### 6.3 玩具算例

6 个有依赖的任务、3 个 agent，枚举 729 种分配，216 种可行，41 个 Pareto 点。在“质量 ≥ 0.80、15.5 小时内完成”下：

| 策略 | 成本 | 工期 | 质量 | 可行 |
| --- | ---: | ---: | ---: | --- |
| 最便宜 | $0.598 | 13.00h | 0.72 | ❌ |
| 最高质量 | $3.160 | 21.07h | 0.95 | ❌ |
| 逐任务贪心 | $0.790 | 15.80h | 0.87 | ❌ 超时 0.3h |
| **约束最优** | **$0.710** | **15.05h** | **0.807** | ✅ |

四个常用启发式全部违反约束，优化器找到了可行解。再压复杂度上限：7.55 就无解，7.60 才有解——说明“过度设计阈值”不能单独拍，必须和工期/质量一起标定。

但这个算例也暴露了真正的瓶颈：**参数估计**。工时、质量、token、过度设计都是估计值；没有历史 trace，优化器就是拍脑袋。所以落地顺序必须是“先记数据，再上求解器”。

## 7. 设计二：动态组织设计

你说“分工架构等因素也要考虑，感觉是个多 agent 的动态组织分工规划，但说不上来”。这个感觉是对的，它有名字：**多 Agent 组织设计**，动态版本叫**动态组织重构**。

### 7.1 六个维度

| 维度 | 要回答的问题 |
| --- | --- |
| Who 组成 | 团队里有哪些角色/agent？固定还是临时组队？ |
| How 协调 | 计划、评审 gate、拍卖、升级、互调？ |
| Which 协议 | supervisor-worker、debate、vote、pipeline？ |
| Structure 结构 | 扁平、层级、矩阵、星型、DAG、市场？ |
| Governance 治理 | 权限/特权、租约、分权、审计、谁负责？ |
| Dynamics 动态 | 什么触发重组？重组成本多大？多久允许变一次？ |

大多数多 agent 系统只设计了 Who + Which，把 How / Structure / Governance / Dynamics 留给临时决定——而这四项才是“组织”。

### 7.2 这是双层优化

```text
上层（战略）：选组织 O =（角色、结构、协调、问责、权限）
              ↓
下层（战术）：给定 O，做任务分配/排期（上一轮的 MILP）
              ↓
操作层：派发、锁、重试、升级
```

上层不能和下层塞进同一个 MILP；可操作的做法是：离散成 3–5 个 archetype → 仿真评估 → 用 bandit 按任务特征选 → 只在批次边界重组，并加重组成本。

### 7.3 管理科学的理论地图

- **Thompson 互依性**：pooled → 标准化+队列；sequential → 计划+交接；reciprocal → 高频互调。
- **Mintzberg 协调机制**：互调、直接监督、工作/产出/技能标准化。
- **Galbraith 信息处理观**：不确定性越高，越需要横向协调，而不是加层级。
- **Ouchi 市场/层级/宗族**：明确任务用市场，模糊任务用层级，长期团队用共享规范。
- **权变理论**：没有唯一最优组织，只有“拟合”。

### 7.4 文献已经走到哪

- **OrgAgent**（2026）：公司式 governance/execution/compliance 三层；层级组织在多数设置下优于扁平；GPT-OSS-120B 在 SQuAD 2.0 上比扁平提升 102.73%、token 降低 74.52%。注意是推理/QA 基准，不是编码。
- **IMACS**（2026）：把 Who / How / Which 解耦；用 bandit 做 Adaptive Org Routing，优于固定协议；**最优问责位置会随模型家族翻转——组织不能硬编码，必须按模型绑定重新验证/学习**。
- **Fluid Structure, Rigid Record**（2026）：执行面可以流动，记录、权限、分权必须刚性；Operation / Review / Supervision 三权分立。原型是小样本，作者没声称通用性能。
- **ARG-Designer**（AAAI 2026）：用自回归图生成，从任务描述直接生成 agent 数量、角色和通信边。

### 7.5 我们的仿真：一个反高潮的结果

为了验证“没有单一组织占优、自适应选组织更好”，我写了一个机制仿真：3 种组织 × 3 类任务互依性，9 个任务，60 个种子。

**结果一：组织选择确实随目标权重大幅变化。**

| 成本/时间权重 | pooled | sequential | reciprocal |
| --- | --- | --- | --- |
| 0.3 / 0.3 | flat | flat | flat |
| 0.1 / 0.1 | flat | hierarchy | hierarchy |
| 0.02 / 0.02 | pipeline | hierarchy | hierarchy |
| 0 / 0 | pipeline | hierarchy | hierarchy |

成本/时间优先时，扁平 peer 全面胜出；质量优先时，层级和流水线才会赢。**这支持“权变”：没有唯一最优组织。**

**结果二：但“动态重组”的收益上限接近 0。**

在质量优先（0.1/0.1）的稳态下：

```text
oracle（每类任务都选最优组织） = 0.804
best fixed（只选一个组织）      = 0.804（hierarchy）
adaptive（bandit 按任务选）     = 0.800
headroom（oracle - best fixed） = +0.000
```

层级组织是一个非常好的“折中组织”：它在 pooled 上只比扁平差一点，在 sequential/reciprocal 上大幅领先。所以按任务动态换组织，几乎没有提升空间，反而要付探索成本。

**结果三：任务组合突变时，固定组织确实会退化，但自适应也没赢。**

阶段 1 以 pooled 为主，阶段 2 切到以 sequential 为主。阶段 1 选出的固定组织是 hierarchy；阶段 2：

```text
fixed hierarchy   = 0.781
adaptive（bandit） = 0.773   （delta = -0.008）
```

自适应反而略差，因为层级本来就稳，探索成本白白付出。

### 7.6 这个负结果怎么读

它不是说“动态组织没用”，而是说：**动态组织的价值上限 = oracle − best fixed，要先测这个 headroom，再决定要不要做。**

Headroom 小，说明存在一个稳健的折中组织，动态重组是过度设计；Headroom 大，才值得付出探索/重组成本。Headroom 什么时候会大？

- 不同任务类型的最优组织差异很大；
- 任务组合在类型间频繁、剧烈切换；
- 固定组织在切换后失效的代价很高；
- 重组本身很便宜（不需要重新培训/重新配置工具）。

我们的仿真里，hierarchy 把这三类任务都“吃住了”，所以 headroom 接近 0。真实的 LLM 场景里，模型绑定、失败率、上下文窗口、工具权限都可能让 headroom 变大——但这需要用真实 trace 去测，不能靠拍脑袋。

## 8. 文献校准：我们的结论和论文对不对得上

| 我们的结论 | 文献对应 |
| --- | --- |
| 纯广播“我要写了”≈ 无效 | CooperBench：通信通道堵塞、承诺不兑现；Informed but Still Colliding：awareness 不等于不冲突 |
| 信息 + 退避把丢失从 61% 降到 2.4%，但不归零 | Passes Alone：一条变更消息恢复 82%，仍有 18% 修不好 |
| 通信 + 原子租约才归零 | MAST 的 inter-agent misalignment / verification；SASE 的 MRP/CRP 把协调物化成可检查的包 |
| 按文件/目录切分比按行切分稳 | Co-Coder：按依赖图/社区切分，比按文件平均切更好 |
| 层级/流水线在质量优先时更优 | OrgAgent：层级在多数设置下优于扁平；但基准是推理/QA |
| 组织不能硬编码 | IMACS：最优问责位置随模型家族翻转，必须按模型绑定重验/学习 |
| 执行可流动、治理要刚性 | Fluid Structure：execution surface 流动，records/permissions 刚性 |
| 复杂度不是默认答案 | Agentless：简单三段式在 SWE-bench Lite 上以 $0.70 超过复杂 agent |

一个重要的反面提醒：**文献里的“多 agent 协作”经常是负收益**。CooperBench 测到协作成功率平均低 30%；MAST 的 14 种失败模式里，inter-agent misalignment 和 task verification 占了两大类。所以“多 agent”不是默认更好，组织设计是必要的补救，不是锦上添花。

## 9. 目前的总判断

### 已经比较确定的

1. **按文件并行的多 agent 开发可行**：契约 + 所有权 + 验收 + git 审计，3 个 agent 可以零冲突交付。
2. **同一文件并发写必须靠原子性**：锁/租约/事务/fencing；通信只能改善，不能解决；check-then-act 不是原子操作。
3. **A2A 是通信层，不是协调层**：它能补 agent 间直连、发现、任务生命周期，但不提供文件锁、验收、治理。
4. **运筹学能优化“给定组织下的分配/排期”**：约束下的 Pareto 解有价值；但参数估计是瓶颈，没有 trace 就不要上求解器。
5. **组织选择是权变的**：成本/时间优先选扁平，质量优先选层级/流水线；没有唯一最优。
6. **动态组织的收益不是自动的**：先测 headroom（oracle − best fixed）；headroom 小的时候，稳健的折中组织比动态重组更划算。

### 还没有答案的

- 10+ agent、跨天/跨周项目、异构模型混用；
- 真实 trace 校准后的组织仿真（现在的仿真参数是人为设定的）；
- 跨 worktree 的合并语义、集成测试归属、合并冲突的自动解决；
- 人工验收的吞吐瓶颈（TOC 说的“瓶颈通常在验收，不在 agent”）；
- 组织重构的成本模型：换组织到底要付多少“重新配置/重新对齐”的代价；
- 安全与权限：agent 能改什么、不能改什么，如何审计。

## 10. 建议的下一步

### P0：先把“可观测 + 可协调”做出来（1–2 周）

- 任务卡：写集、依赖边、DoD、验收标准；
- 原子 claim/lease（TTL + fencing token）；
- 每次运行记录 token、工时、质量、diff 规模、返工原因；
- 人工验收队列。

**没有这些数据，后面的优化和组织设计都是空谈。**

### P1：可配置组织，不是动态组织（2–4 周）

- 先实现 2–3 个 archetype：flat、supervisor-worker、pipeline；
- 用配置切换，不自动切换；
- 在真实任务上测“组织 × 任务类型”的收益矩阵；
- 计算 headroom：每类任务的最优组织 vs 最佳固定组织。

### P2：约束下的分配/排期（1–2 月）

- 用历史 trace 估计 cost/quality/duration；
- 任务 ≤50 时上 CP-SAT，输出 Pareto 前沿；
- A/B 对比贪心，指标是成本、质量、周期、返工率。

### P3：只有当 headroom 足够大，才做自适应

- 用 bandit/规则在批次边界选组织；
- 加重组成本和稳定性惩罚；
- 先 shadow mode：优化器只建议，不自动执行。

### P4：跨边界才用 A2A

- 同工作区继续原生 subagent；
- 跨机/跨厂商/外部 agent 用 A2A；
- 工具层用 MCP，编辑器集成用 ACP。
