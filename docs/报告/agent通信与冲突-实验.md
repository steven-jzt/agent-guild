# Agent 之间通信、共享信息，能不能解决“打架”？

> 配套实验：`coordination/`。接《多 agent 同工作空间-实验报告》和《A2A-可行性-附记》。

## 0. 结论

**能改善，但不能解决。** 而且“改善”有严格前提：**收到信息后必须据此改变行为**。

- 只广播“我要写了”、但没人避让：**等于没通信**（和同样节奏的静默组完全一样）；
- 收到意图就退避重试：丢更新从 61% 降到 **2.4%**，但多数轮次仍会丢 2–4 次；
- 通信 + 原子租约：**0 丢失**，而且比退避重试更快；
- 不通信、只做“读版本→校验→写”：**仍丢 38%**——check-then-act 不是原子操作。

一句话：**通信解决“知不知道”，原子性解决“能不能同时”。**

## 1. 实验设计

3 个 agent（独立进程）对同一个 JSON 计数器各做 30 次「读—改—写」，期望 90。全部通过一个 TCP 消息 broker 通信，跑 6 种协议、每种 5 轮：

| 协议 | 通信？ | 收到信息后行动？ | 原子性？ |
| --- | --- | --- | --- |
| `silent` | ❌ | — | ❌ |
| `paced` | ❌ | — | ❌ |
| `announce` | ✅ 广播意图 | ❌ 不避让 | ❌ |
| `polite` | ✅ 广播 + 接收 | ✅ 退避重试 | ❌ |
| `lease` | ✅ 申请/授予 | ✅ 拿到锁才写 | ✅ 中心化互斥 |
| `cas`（read-validate-write） | ❌ | — | ❌（check-then-act） |

`paced` 是对照组：和 `announce` 一样先等 20ms 再写，但不发任何消息，用来隔离“错峰”效应——否则会把“慢一点”误当成“通信有用”。

## 2. 结果（5 轮平均）

| 协议 | 最终计数 / 90 | 丢失 | 丢失率 | 重试 | 消息 | 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `silent` | 35.0 | 55.0 | **61.1%** | 0 | 0 | 0.15s |
| `paced` | 42.8 | 47.2 | 52.4% | 0 | 0 | 0.76s |
| `announce` | 43.0 | 47.0 | **52.2%** | 0 | 90 | 0.77s |
| `polite` | 87.8 | 2.2 | **2.4%** | 70.8 | ~86 | 2.44s |
| `lease` | **90.0** | **0.0** | **0%** | 0 | 180 | 0.38s |
| `cas` | 55.4 | 34.6 | **38.4%** | 39.8 | 0 | 0.26s |

原始逐轮数据在 `coordination/` 的运行输出里；`polite` 各轮丢失为 0/3/2/4/2，`announce` 各轮 final 在 30–64 之间波动。

## 3. 四个发现

### 3.1 纯信息共享 ≈ 没有共享

`announce` 43.0，`paced` 42.8。两个数字几乎一样（考虑逐轮波动，这点差异没有意义）。

这说明：**广播“我要写了”本身不产生任何协调效果。** 之前 `announce` 比 `silent` 好看（43 vs 35），几乎全部来自“多等了 20ms”带来的错峰，而不是信息。把节奏控制住之后，通信的净效果接近于 0。

> 对 LLM agent 的直接含义：在提示词里写“写之前先告诉其他 agent”而没有强制的避让/锁机制，基本等于没写。

### 3.2 信息 + 行动，能大幅改善，但不能归零

`polite` 把丢失率从 61% 压到 2.4%，这是实打实的改善：agent 收到别人的意图后主动退避，碰撞窗口大幅缩小。

但仍有丢失：5 轮里有 4 轮丢了 2–4 次，原因是**信息永远是过期的**：

```text
A: 看 inbox —— 没人要写
B: 看 inbox —— 没人要写      ← 同一瞬间
A: 广播 + 写
B: 广播 + 写                  ← 都认为自己安全
```

两个 agent 可以基于同一份“旧信息”同时做出“现在安全”的判断。**没有原子裁决点，就无法排除这种同时性。**

### 3.3 通信 + 原子租约，才真正归零

`lease` 90/90，零丢失。关键不在“发了消息”，而在 broker 的 `acquire` 是一个**原子裁决**：同一时刻只有一个 agent 能拿到 grant，其他人排队。

有意思的是它还最快（0.38s vs `polite` 2.44s）：**退避重试的浪费，比排队等待更贵**。当然这不意味着锁永远更快——这里的 lease 没有网络重试和锁竞争退避，只是一个机制对比。

工程上要注意**租约过期**：如果持有者 GC 停顿/网络分区，租约到期后可能被第二个 agent 拿走，而第一个还在写。生产上用 **fencing token**（单调递增的 epoch，存储层拒绝旧 epoch 的写）来兜底。

### 3.4 “先检查再写”不是原子操作

`cas` 的设想是：读版本 V → 等等 → 再读一次，还是 V 就写。听起来像乐观并发控制，实际仍丢了 38.4%。

原因：

```text
A: 读 version=7
B: 读 version=7
A: 复查 version=7 → 写 version=8
B: 复查 version=7 → 写 version=8   ← 覆盖了 A
```

**检查和写之间有一个窗口，两个 agent 可以同时通过检查。** 真正的 CAS 必须是“比较并交换”由同一个原子操作完成（CPU 指令、数据库行锁、文件锁、对象存储的 ETag 条件写），而不是“读两次再写”。

这条也解释了为什么上一轮 DSH 的 `write` 工具能可靠拒绝过期快照：从行为看，校验与写入在同一个受控路径里串行完成，没有给其他 agent 留下“检查完再写”的窗口；而 agent 一旦改用 shell/Python 直接写文件，就退化成 `cas` 这种 check-then-act，保护消失。

## 4. 2×2 定位

| | 无原子性 | 有原子性 |
| --- | --- | --- |
| **无通信** | `silent`：61% 丢失 | 本地锁 / 数据库事务：0 丢失（上一轮已验证 180/180） |
| **有通信** | `announce` 52%；`polite` 2.4% | `lease`：0 丢失 |

结论很清楚：**决定“会不会丢”的是原子性这一列；通信决定的是“协调成本”和“语义质量”，不是正确性。**

## 5. 那通信到底有什么用？

通信不是没用，而是要用在它擅长的地方：

| 用途 | 效果 |
| --- | --- |
| 任务分派 / 认领 | 减少重复劳动，但认领动作本身要原子（CAS 任务板） |
| 意图广播 + 变更通知 | 让其他人**重读**，减少基于过期快照的写；配合版本校验才安全 |
| 语义对齐 / 契约澄清 | 减少“接口理解不一致”这类返工 |
| 冲突上报 / 升级求助 | 让 agent 停下来问，而不是猜 |
| 协商边界（谁写哪个文件） | 把冲突从运行时前移到规划时 |
| **替代锁** | ❌ 不能；消息不是互斥量 |

对上一轮“同工作空间”的场景，最实用的组合是：

1. **规划期**：用通信把文件所有权分好（谁写 `storage.py`、谁写 `cli.py`）；
2. **运行期**：共享文件用原子 claim（锁文件/数据库行/租约），不要靠“我会通知你”；
3. **写之后**：广播“X 已变更”，让相关 agent 重读 + 版本校验；
4. **冲突时**：退避重试是改善手段，不是正确性保证；最终要有单写者或事务兜底。

## 6. 对 A2A / DSH 的含义

- A2A 提供的是**消息通道**（SendMessage、Task、Artifact），不是锁服务。用 A2A 做协调，必须把“锁/租约”做成一个独立的 coordinator agent 或共享存储，并且裁决必须是原子的。
- 如果只是让 agent 互相通知“我要改了”，从本实验看，**收益接近于零**——除非接收方真的改变行为。
- DSH 原生 subagent 之间不能直接通信，但 `write`/`edit` 工具自带快照校验；这比“能聊天但没有原子性”更接近正确性。**不要为了通信而放弃工具层的保护。**
- 真正需要补的是：跨进程/跨机的原子 claim（文件锁、SQLite 事务、etcd/Redis 租约），以及变更通知（A2A 或事件总线）。

## 7. 局限

- 这是**机制级模拟**：3 个 Python 进程、单机、无网络分区、broker 单点；不是 LLM agent 的真实推理延迟。
- LLM agent 还会引入“收到消息但不遵守”“退避后忘记原任务”“消息理解偏差”等新问题，真实场景的 `polite` 大概率不会比 2.4% 更好，可能更差。
- `cas` 的 38.4% 是“读两次再写”的实现；真正的原子 CAS 不在此列。
- `polite` 的 2.4% 对参数敏感：意图窗口、退避时长、agent 数量、写操作耗时都会改变结果；换一组参数可能更差，也可能出现活锁。
- 计数器的写是整文件覆盖，和 LLM agent 用 `write` 整文件覆盖的行为同构；`edit` 的精确匹配冲突是另一类问题（会显式报错）。

## 8. 复现

```powershell
cd coordination
python run_experiment.py
```

输出包含每种协议 5 轮的 final / lost / retries / messages / 耗时，以及平均值。
