## 四、代码层面的具体发现

### 4.1 做得扎实的部分

- **`JobHost.cs`（83 行手写 P/Invoke）** 是真的工程：`CREATE_SUSPENDED` 创建 → 分配 Job → `ResumeThread`，`KILL_ON_JOB_CLOSE`，并监听父进程句柄。单测实际验证了"所有者死亡后子、孙进程都消失"。这不是 `child.kill()` 糊过去。
- **`dsh-outcome.ts`** 把"协议成功"和"模型失败"分开，且 M0 记录写了做过**变异验证**（反转判断条件 → 测试确实失败）。这是有意识的测试有效性检查。
- **`workspace.ts`** 用 `clone --no-local` + 独立裸库 + Worktree，测试断言源仓库 HEAD 与 status 均未变。
- **物理路径解析**（`realpathSync.native`）解决的是一个真实踩过的坑（LocalAppData 重定向导致 `CreateProcessWithLogonW failed: 267`），且留了回归测试。

### 4.2 值得修的问题

| 严重度 | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| 🔴 高 | `managed-process.ts:12-21` | 运行时用 `csc.exe` 编译 `JobHost.cs` 到 `%LOCALAPPDATA%\AgentGuild\bin` 并**直接执行**；只要同名 `job-host-<hash>.exe` 已存在就无条件信任，不校验内容 | 产品化时随包分发**已签名**的 exe；或至少校验文件哈希后再执行。同用户攻击面有限，但这属于"可写目录里信任可执行文件"的经典形态 |
| 🟠 中 | `package.json` 依赖面 | 2 个直接依赖拖入 **1000 个包 / 571 MB**。其中 `@deepseek-ai` 作用域独占 330 MB，含 `libreoffice-kit-win32-x64`（**182 MB**，一整套 LibreOffice）、`sherpa-onnx`（语音）、`node-pty`、`dsh-web-frontend`（整套前端产物） | M0 只需要 DSH 的 runtime + stdio 协议，却装了完整发行版。建议单独评估 `dsh-sdk-minimal` 之类的裁剪路径，否则"实验工程"比很多产品还重 |
| 🟠 中 | `cancel-smoke.ts:20` | Codex launcher 路径**写死** `%APPDATA%\npm\...`，不读 `AGENT_GUILD_CODEX_JS` | 换机后 `npm run m0` 能跑、`npm run m0:cancel -- codex` 直接失败。文档第 227 行承认了，但这是最容易让接收方卡住的一处 |
| 🟠 中 | `rpc-process.ts:65-74` | 请求超时后只在本地丢弃 pending，**没有"核对厂商侧是否已执行"的机制** | 这正是架构文档 9.2 要求的能力，M1 必须补；当前注释只写了"不自动重发"，没说"超时后执行状态未知要人工核对" |
| 🟠 中 | `codex.ts:11` | 回合超时固定 180s，与事件活跃度无关 | 长任务静默期会被误判超时，与文档自己写的"静默运行不等于失联"冲突 |
| 🟡 低 | `rpc-process.ts:60-63` | `stdin.write` 忽略返回值，无背压处理 | 超大 prompt 时内存可能膨胀 |
| 🟡 低 | `managed-process.ts:10` | `process.env.LOCALAPPDATA!` 非空断言 | 环境缺失时得到畸形路径，类型系统把风险藏起来了 |
| 🟡 低 | `dsh-launch.ts:9` | patch 文件里写入用户 `~/.dsh/.credentials.yaml` 的**绝对路径**，且 `watch: true` | 该文件若被日志采集，会泄漏本机目录结构 |
| 🟡 低 | 测试结构 | 17 项中真正有真实副作用的只有 3–4 项（Job 进程树、Git 工作区、物理路径），其余是 fixture 级协议测试 | 合理，但"17 项通过"的信息量低于数字给人的印象 |

## 五、交接包本身的问题（与代码无关）

1. **泄漏作者机器名**：`README.md:21` 和 `docs/M0_验证记录:51` 出现 `C:\Users\LENOVO\...`。发给同学前建议脱敏为 `C:\Users\<你的用户名>\...`。
2. **没有 LICENSE**：一份要交给别人改的代码，没有版权与授权声明，法律上是"保留所有权利"。建议明确是内部协作还是开源。
3. **`package.json` 缺 `repository` / `license` 字段**。
4. **没有 CI**：17 项测试只靠手跑，"测试通过"依赖每次口头确认。建议加一个最小 workflow（`npm test` + `typecheck` + audit 阈值），让这句话可自动复算。
5. **无 `.editorconfig` / 无 `CHANGELOG`**：接收方容易在此类细节上反复踩坑。
6. **无 `.git`**（已声明），代价是"代码 = a58e08e"不可验证。

## 六、我的判断：这份包到底值不值

**值得接，但要认清它是什么。**

它的强项是**诚实度**：
- 主动区分"设计版本 v1.0.1"与"代码版本 0.1.0"；
- 主动写"上面这整条流程还没有实现"（第 21 行）；
- 主动写"没有 Web 后端接口、Electron IPC 接口、数据库表或 React 页面"（第 115 行）；
- 主动写"面试官最容易在界面上简化掉的部分"（第 152 行）。

这在交接材料里是稀缺品质——大部分交接包会把"计划"写成"已有"。

它的弱项是**底座**：一个前端同学拿到它，**没有任何接口可以联调**。第 8 节那句"需要先约定接口"才是这个包目前最核心的交付缺口。

**风险提示**：198 个 high 漏洞 + 182 MB 的 LibreOffice 被无声拖进依赖树，说明依赖决策缺少审查环节。这个习惯如果延续到 M1，会在打包阶段集中爆发。

## 七、如果我来安排下一步（按优先级）

1. **先定契约，再写界面。** 产出「适配器接口 + 事件类型 + 交互请求类型」的 TypeScript 类型文件 + 一个 MockAdapter，让前端可以在 M1 不存在时并行开发。这一步成本最低、解锁最多。
2. **修 3 个可用性坑**：`m0:cancel` 读 `AGENT_GUILD_CODEX_JS`；超时后打印"执行状态未知，需人工核对"；`LOCALAPPDATA` 缺失时明确报错。
3. **给出依赖处置清单**：把 198 个 high 分成"可升级修复 / 传递依赖无修复 / 仅开发期"，并明确 `npm audit fix --force` 禁止使用（文档已警告，但没给替代方案）。
4. **补 CI**：`npm test` + `typecheck` 变成自动门禁，"17 项通过"不再依赖口头。
5. **脱敏 + 补 LICENSE**：两处 `C:\Users\LENOVO` 和一个 LICENSE 文件，10 分钟的事。
6. **UI 侧只做五屏对照表**（文档第 8 节已经列好），用 mock 数据，不碰 Git、不碰凭据、不碰数据库。

**不要做的**：现在就去实现 M1 的 SQLite 与状态机。M0 还有 7 项待验证（文档第 7 节），其中 API 路线的停止/接续是关键——先证明"能可靠停下并接上"，再谈协作规则，否则 M1 的门禁全部建在流沙上。

## 八、与本工作区已有成果的关系（重要）

这个交接包**不是在与 `p0-coordinator` 竞争，两者正好互补**：

| 层 | 交接包（本 ZIP） | 工作区 `p0-coordinator` |
| --- | --- | --- |
| SQLite / 任务 / 租约 / 事件 | ❌ 无（全部在内存 + JSON） | ✅ 有，91 个单测 |
| Run / Candidate / Worktree / Merge 门禁 | ❌ 只有目标架构文档 | ✅ 有实现（`v1_*` 系列） |
| 人工验收 / N-of-M 审批 | ❌ 无 | ✅ 有 |
| **Codex / DSH 协议级适配** | ✅ **app-server + JSON-RPC + 提问/审批桥接** | 🟡 `adapters.py` 是**子进程 + argv** 级别，没有协议状态机 |
| **Windows 进程树治理** | ✅ **Job Object（手写 P/Invoke）+ 子孙进程清理测试** | 🟡 `subprocess` + 超时 |
| **物理路径 / LocalAppData 重定向** | ✅ 已解决并留回归测试 | ❌ 未见 |
| Electron / UI | ❌ | 🟡 WebView2 壳（Electron 崩） |

**结论：该拿的是 `src/transport/` + `src/adapters/` + `JobHost.cs`，不是"照它的架构重做一遍"。**
把这三块嵌进 p0 的 adapter 层，p0 立刻从"能跑 CLI 的协调器"升级为"能接管真实 Codex/DSH 会话、能干净杀进程树的协调器"。
反过来，p0 的 Run/Candidate/Merge 正是这个包 M1 想做的事情——交接包里一行都还没有。

如果两边各做各的，就是在同一个项目上重复投入两遍。**最省力的路线是：以 p0 为骨架，把本包的传输层移植进去，然后只在 UI 层做新工作。**
