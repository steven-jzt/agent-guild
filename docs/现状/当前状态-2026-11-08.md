## 3. 关键设计决策

1. **单机 SQLite，不引入 Temporal/K8s**：`BEGIN IMMEDIATE` + TTL + fencing 足够 P0；跨机再换 Postgres。
2. **MCP + CLI 双入口**：支持 MCP 的客户端挂 server；shell-based agent 用 `worker_cli.py`。
3. **自报与验证分开**：`runs.quality` 是 worker 自报，`verifications.score` 是独立 verifier 打分，不混为一谈。
4. **审批是计数制 + TTL**：N 个不同 approver，票会过期；旧票 superseded，不重复计数。
5. **预算是硬止损**：只按已记录 `runs.cost_usd` 累计，不预测未来花费。
6. **计划可回写**：MILP 的 assignment 写入任务板 + reservation，`claim_planned` 按计划领取。

## 4. 已知边界

- **真实 token/cost 未接**：live demo 的 cost/tokens 是 0；quality 是自报，验证分是 checks 通过率。
- **审批没有角色/顺序/自动升级**：只有 N 个不同 approver + TTL；alice/bob 是脚本调用，不是真人。
- **command check 不是 OS 沙箱**：有 allowlist、`shell=False`、timeout、输出上限、环境变量白名单，但没有 cgroup/容器级隔离。
- **单机**：无跨机 lease、无 Postgres、无鉴权/ACL。
- **V1 核心完成第六块**：Run、预约、Candidate/Merge、Worktree/越界 diff、Task lifecycle、双重门、Adapter 合同都有；**DSH 5 个任务、Codex（DeepSeek）1 个任务、3-agent 并发（DSH + Codex-DeepSeek + Codex-智谱）全部合入；Codex App Server adapter 已跑通 V1 端到端；Electron 崩，WebView2 壳已跑通 Start Run/Approve/Merge**。
- **双重门但不是自动同步**：`claim_task` / `start_execution` 同时检查 `write_set` 与 `file_reservations`；但没有从 `write_set` 自动生成 reservation，仍需显式 `reserve_files`（或 V1 调度器预建）。
- **无内容合并**：预约/Worktree 只保证范围互斥，不保证语义合并；Document Kernel 还没实现。
- **无优先级抢占**：高优先级任务不能抢走低优先级租约。
- **计划器规模小**：CBC 在 6 任务玩具算例上跑通；50 任务/CP-SAT 还没做。
- **live demo 覆盖 happy path**：拒绝/超时/预算超支有单元测试或脚本 demo，但没在真实 agent 上跑。

## 7. 与 Agent Guild V1.0.1 的对比

对照 V1.0.1《计划与架构总结》：[AgentGuild-v1.0.1-对比分析.md](../评审/AgentGuild-v1.0.1-对比分析.md)。

一句话：**我们做的是“协调内核 + 验证/审批原型”；V1 要的是“桌面产品 + Run/Candidate/Git 合入门禁”。**

- **可复用**：SQLite、任务/租约/fencing/事件、verifier、N-of-M 审批、CLI/MCP 调用形态；
- **关键错位（原始分析）**：`runs` 原本只是遥测，V1 的 Run 是执行实体；现在已拆出 `executions`，并补了 Candidate/SHA/Worktree/Merge；
- **必须新建/接真**：`executions`、`file_reservations`、`candidates`、`merge_attempts`、`evidence`、`workspaces`、`lifecycle` 已实现；Codex/DSH/App Server 已真实接入；Electron 崩但 WebView2 壳已通过。
- **建议**：先做 V1 M0（三条接入链路），再改核心领域模型，最后才做 UI；预算/Pareto 后置。
