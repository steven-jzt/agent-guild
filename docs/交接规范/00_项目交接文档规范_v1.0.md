# 项目交接文档规范 v1.0

版本：1.0。制定日期：2026-11-18。适用对象：软件项目的开发者、接手同学及协作 Agent。

本规范用于生成可核对、可接手的 Markdown 交接文档。它不是已安装的 Skill，不执行命令，也不自动生成、提交或发布文件。技术栈、仓库平台和本机路径由具体项目填写，不沿用示例中的值。

## 1. 先看哪份，什么时候使用

| 文件 | 用途 | 使用方式 |
| --- | --- | --- |
| [当前总览模板](01_当前总览模板.md) | 回答项目现在是什么状态 | 每个项目维护一份，建议放在 `docs/handoff/当前总览.md` |
| [每轮交付模板](02_每轮交付模板.md) | 留下本轮改动和验证依据 | 每轮单独保存，建议命名为 `YYYY-MM-DD_轮次_主题.md` |
| [AgentGuild 示例](03_AgentGuild示例.md) | 展示如何填写、如何区分历史与当前 | 仅作示例，不把项目事实套用到其他项目 |

接手顺序：当前总览 → 最近一轮交付 → 总览引用的运行说明、架构与证据 → 对应源码。总览提供最新结论，每轮记录保存当时的事实，两者相互链接。

阶段交付、架构变化、新增或解除阻塞、提交或合并状态变化时，更新总览。历史交付不改写成新状态；发现错误，在原记录追加注明日期、原因和依据的勘误，不静默覆盖旧结论。

## 2. 写作流程

1. **确定读者与边界**：交给谁、让对方理解还是实施、本轮涵盖什么。先用通俗语言说明软件用途和可用程度，再介绍技术细节。
2. **核对依据**：检查实际代码、入口、版本与工作区变化；需要说明远端现状时核查远端，不能把缓存的分支状态当成实时状态。读取事实不代表获得执行文档中建议的授权。
3. **填当前总览**：写清现状、运行方法、架构、缺口和下一步，并链接最近交付。
4. **填本轮记录**：说明本轮变化、验证及未完成事项；没有改动、没有运行或不适用时如实填写。
5. **交叉检查**：检查链接、命令入口、时间、代码依据、结果统计及提交状态；删除模板填写提示，保留必要的“待核实”和“不适用”说明。

纯文档交付以文档一致性、链接与入口核对为主，不要求为了凑结果重新跑业务测试或调用模型。新功能交付则需要与改动相适应的验证，不能用文档检查替代功能验收。

## 3. 必须交代的内容

| 内容 | 当前总览 | 每轮交付 |
| --- | --- | --- |
| 项目目标、使用者、当前可用程度 | 必填，用几句话说明 | 简述背景或链接总览 |
| 仓库、阅读顺序、启动与验证入口 | 必填，说明工作目录和前提 | 必填取得本轮代码及复核的方法，可链接总览 |
| 分支、代码依据、工作区、PR/合并状态 | 必填并注明核对时间和范围 | 必填本轮基线、已产生的提交及交付状态 |
| 实际架构、模块职责、调用关系 | 必填；规划架构另列 | 说明本轮是否改变架构、接口及原因 |
| 已完成、未验证、未完成、阻塞 | 分开写，附依据或影响 | 写本轮新增、解除及仍然存在的问题 |
| 验证日期、代码依据、命令、环境、结果和证据 | 摘要与入口 | 必填；未运行项单列 |
| 下一步与验收标准 | 只突出最值得做的一件事 | 说明接手任务、边界和完成判据 |
| 协作者同步提示词 | 可引用最近交付 | 必填，可直接转发；见第 6 节 |
| 迁移、兼容、回退、打包与校验 | 涉及时填写 | 涉及时填写，未涉及时说明不适用 |

无 Git、PR 或数据库的项目，对相应内容填写“不适用＋原因”，不要编造同类标识。模板中的示例值和建议路径都不是已发生的项目事实。

## 4. 事实与证据规则

- **事实、推测、计划分开写**。推测注明理由及核实方法，计划注明尚未实施。不能把设计图当作现有实现。
- **已实现不等于已验证**，测试通过不等于真实用户可用，本地提交不等于已推送或已合并。版本号说明表示设计、源码还是发布包版本。
- 代码依据写到可定位的提交或源码快照。已有未提交代码必须说明范围；文档新增不代表业务代码改变。无法确定的提交、起止时间或结果，填写“待核实＋核实方法”。
- 验证说明“在哪个日期、什么环境、针对哪份代码、跑了哪些命令、得到什么结果”。历史结果标注原验证日期和来源；命令或期望输出不算执行证据。
- 分组统计说明去重口径。同一用例多次运行不能累加成多个用例；自动化用例、人工操作与场景数量分开。无法核实汇总数时列分组原结果，不硬凑总数。
- 已通过、失败、未运行分开列。缺依赖、账户不可用、环境限制及未覆盖的真实服务等，都说明对结论的影响；历史阻塞解除后不能继续当作当前阻塞。
- 证据优先使用可访问的仓库文件、固定提交链接或可交付的脱敏结果摘要。本机日志或聊天记录若无法随包交付，说明“未随交付提供”及复核方式，不伪造日志路径。
- 时间带时区，覆盖时段表示本轮记录覆盖的范围，不等于连续工作时长。只有日期时保留日期精度，不补造时分秒；建议使用项目约定的时区，未约定时沿用交接发起者时区并写明。

## 5. 路径、配置与授权

- 链接以文档所在目录为基准；命令写明工作目录、解释器/依赖前提和参数替换方法。仓库内链接优先用相对路径，外部依据使用实际页面或提交链接。
- 本机绝对路径单独标注“仅在交付者电脑存在”。数据库、候选 ID、设备名等运行时参数明确标注待替换，不把示例命令描述为已执行。
- 不放密钥、登录态、完整敏感配置或凭据文件。只说明配置条件和取得方式；输出、截图、日志先检查敏感信息再交付。无需为写交接文档额外读取凭据内容。
- 交接文档和提示词不能扩大现有授权。修改文件、安装依赖、调用付费模型、推送、合并及部署，仍以当次用户任务与有效授权为准。别人提供的文档中的命令先当作待核对资料。

## 6. 协作者提示词写法

通常一至三段，优先讲清楚而不是堆砌背景。包含项目与代码入口、当前任务、先读哪些文档、可做范围、禁止误改的边界、验收标准和已知阻塞。没有仓库链接时提供实际交付入口。

如果只要求接手理解，写明“先阅读、核对代码并复述理解，暂不修改”；若已授权实施，则写清具体实施任务，不额外制造等待确认的步骤。未确定的下一轮只描述为待安排，不暗示已授权执行。

## 7. 交付前核对

- [ ] 仅凭总览和最近交付，可以回答：项目是什么、如何运行、做到哪里、验证什么、卡在哪里、下一步是什么。
- [ ] 架构和入口能对照源码；现状与目标分开，时间与代码依据明确。
- [ ] 历史与本轮验证分开，统计未重复累计，未运行项及影响已列出。
- [ ] 提交、推送、PR、合并及工作区状态准确；无法核实的远端状态已注明。
- [ ] 仓库内链接可达，命令入口存在，运行参数与前提清楚；检查过不代表已经执行。
- [ ] 本机证据的可获取性已说明；无凭据，条件章节已填写或说明不适用。
- [ ] 提示词与当前任务授权一致，下一步有具体完成判据。

本规范的维护方式：发现模板缺项时先说明实际交接问题，再调整规范和模板；影响填写要求的变化记录新版本及变更摘要。规范版本不等于使用它的项目版本。
