## 1. 先用功能理解这个项目

Agent Guild 是一个本机使用的“多 Agent 项目控制台”。用户创建任务，手动指定 Codex 或 DeepSeek Harness（DSH）去执行；软件负责记录过程、隔离工作区、协调修改范围、组织检查和验收。

最终希望跑通的例子：

> 新建“修复保存按钮”的任务 → 指定 Codex → 查看进度、回答问题 → 平台跑测试 → DSH 审查 → 用户实际操作验收 → 用户另行确认合入项目。

**上面这整条流程还没有实现。** 目前只验证了其中“启动真实 Agent、让它在实验工作区改文件、采集结果、停止后重新接续”的部分。

V1 的范围已经确认：Windows x64 优先、本机单用户、管理员手动派遣、接入已有 Agent。自动抢任务、远程多人、自研 Agent 执行引擎、完整终端等不在当前短期范围内。

## 3. 已经实际完成的工作

### 3.1 工程与通信基础

- 建立 Node.js + TypeScript 实验工程，固定依赖版本并保留锁文件。
- 实现 JSONL 分帧、分段接收、帧大小限制与异常帧处理。
- 实现 JSON-RPC 请求 ID 关联、超时、服务端提问响应和关闭时拒绝待处理请求；超时不自动重复执行。
- 实现 Windows 原生 Job Object 启动助手，管理所属执行进程树。测试包含所有者退出后清理子、孙进程，以及中文、空格、引号参数。
- 修复打包桌面环境的 LocalAppData 重定向路径问题：先解析物理路径，再交给执行端，保留 Codex 原生沙箱。

### 3.2 三条真实接入路线的基本任务

| 路线 | 实际做过的验证 | 当前结论 |
| --- | --- | --- |
| Codex | app-server 握手、接收任务与事件、修改限定文件、平台独立测试 | 基本任务通过 |
| DSH 账号 | 官方客户端连接 Runtime，使用已有账号凭据完成同一任务 | 基本任务通过 |
| DSH API Key | 独立选择 API Provider 完成同一任务 | 基本任务通过；原 401 阻塞已解除 |

三条基本任务都在专门生成的测试项目中进行；只允许修改 `src/total.ts`，平台另外跑 2 项测试，并检查实验源仓库未变化。没有拿用户真实业务项目做修改或合并。

DSH API Key 最初确实返回过 AUTH / 401。用户于 2026-11-08 更新本机密钥后，复测通过。这是历史故障，不是当前仍在等待用户处理的阻塞。

### 3.3 交互与中断的部分验证

- DSH 账号路线：观察到真实 `user-question/ask`，回传固定测试答案后继续。
- DSH 账号路线：只读 `plugin_manager list` 触发真实 `approval/request`，平台拒绝该审批。
- Codex：在命令执行中停止宿主，新建 Runtime/会话后，从保留工作区接着完成任务。
- DSH 账号：在等待问题答案时停止宿主，新建 Runtime/会话后接续任务。
- 已区分协议状态和模型结果：DSH 显示 idle、`session/wait` 成功，不代表模型没有鉴权错误；代码另行检查回合错误。

提问测试使用的是预设回答，审批测试使用的是预设拒绝；它们证明通道能工作，**没有实现真人操作界面，也不算任务的人工验收**。

## 4. 当前代码架构：现在就能看到什么

现有代码运行方式是命令行实验脚本，实际调用链如下：

```text
实验脚本（src/experiments）
  ├─ 生成测试源仓库 → 独立裸克隆 → Worktree
  ├─ CodexAdapter → RpcProcess → Windows JobHost → Codex app-server
  ├─ DSH 基本实验 → 官方 HarnessClient → Windows JobHost → DSH Runtime
  └─ DshAdapter → RpcProcess → Windows JobHost → DSH SDK stdio 协议

实验结束 → 平台单独运行测试/检查文件范围与源仓库 → 保存脱敏报告与事件
```

| 源码位置 | 职责与接手提示 |
| --- | --- |
| `src/transport/json-lines.ts` | 协议流的分帧；不负责业务状态 |
| `src/transport/rpc-process.ts` | 请求、响应、事件、超时、关闭；是实验通信层 |
| `src/transport/JobHost.cs`、`managed-process.ts` | Windows 原生执行树管理及助手编译缓存；不能替换成仅终止一个 PID 就宣称等价 |
| `src/adapters/codex.ts` | Codex 的初始化、线程和回合执行、事件及结束处理 |
| `src/adapters/dsh.ts`、`dsh-outcome.ts` | DSH 的原生提问/审批桥接及模型回合错误识别 |
| `src/experiments/workspace.ts` | 实验仓库生成与独立工作区；还不是产品级项目管理器 |
| `src/experiments/dsh-launch.ts` | 隔离实验配置并引用官方凭据服务；没有把凭据打进包 |
| 其他 `src/experiments/*.ts` | 基本任务、交互及取消接续的验证入口；不是给 UI 直接调用的产品 API |
| `test/` | 17 项行为测试；含模拟协议服务，也含真实本地进程生命周期测试 |

**目前没有 Web 后端接口、Electron IPC 接口、数据库表或 React 页面。** 同学不能直接按一套已经存在的 HTTP API 开始联调，需要先约定接口。

## 5. 目标架构：已经确定，仍待实现

采用模块化单体，本地运行，暂不拆远程服务：

```text
用户
  ↕
React + TypeScript 界面
  ↕ 受限 Electron IPC
Electron 主进程（窗口、托盘、受限入口）
  ↕
独立 utilityProcess 中的协作核心
  ├─ SQLite：任务、Run、预约、候选、验收等状态，核心单点写入
  ├─ 文件：详细事件、测试证据、交接摘要
  ├─ 执行管理与适配器 → Codex / DSH
  ├─ 平台管理的独立 Git 工作区
  └─ 候选验证 → Agent 审查 → 人工验收 → 单独确认合入
```

目标软件有三层可以分别理解：界面供人操作，协作核心执行规则和记账，适配器负责与具体 Agent 通信。目前主要做了第三层的实验基础，第二层和第一层还没有落地。

SQLite 访问组件、迁移方案、Electron 版本及 Windows 打包细节尚未验证；包内也没有安装 Electron、React 或 SQLite 依赖。`package.json` 中只有当前实验所需依赖。

## 6. 后续开发不能丢掉的规则

- 管理员手动指定作者和审查 Agent；V1 不做自主认领。
- DSH API Key 与官方账号登录都要支持，分别验收；认证失败不能静默切换另一条路线。
- Task 是目标，Run 是一次执行，Candidate 是不可变交付候选。重试、返修、换 Agent、接续都创建新 Run，保留旧记录。
- 旧 Run 的迟到事件或审批不能影响新 Run。
- 文件范围预约属于任务；待验收、进程退出或超时不自动释放，合入或撤回后才按规则释放。
- 平台管理库独立于用户源仓库，Windows 路径规范化；文件及父子目录的占用冲突都需要处理。
- 越界修改保留证据并禁止通过平台合入。这不是阻止所有磁盘访问的操作系统沙箱。
- Agent 自报、平台实际采集、自动测试和人工结论分别记录；“进程结束”“模型说完成”都不是验收通过。
- 每个任务都需要人工验收；验收通过后还要单独确认合入。测试、审查、人验与合入必须针对同一候选；基线或候选变化后重新检查。
- 用户源仓库脏状态等条件不满足时阻止合入；不能用 `reset --hard`、`clean` 或强行覆盖来掩盖问题。
- 详细规则及恢复边界见 v1.0.1 架构总结；以上是接手时最容易被界面简化掉的部分。

## 9. 接收方怎样复现现有工程

将压缩包解压到自己的开发目录，例如 `D:\Dev\AgentGuild`；进入其中的 `agent-guild` 目录运行。现有实验优先在非云同步目录复现。

环境要求：Windows x64、Node.js ≥24.9、npm、Git；Windows JobHost 首次运行使用系统 .NET Framework 的 `csc.exe` 编译。原机器版本为 Node 24.15.0、npm 11.12.1、Git 2.54.0.windows.1、Codex 0.164.0。

```powershell
# 在解压后的 agent-guild 目录中执行
npm ci
npm test
npm run typecheck
```

自动化测试和类型检查不需要接收原作者的密钥或登录态。真实模型实验需要接收方自行在本机配置合法可用的 Codex / DSH 官方认证，可能消耗相应模型用量：

```powershell
npm run m0
npm run m0:dsh -- account
npm run m0:dsh -- api-key
npm run m0:dsh:interaction
npm run m0:cancel -- codex
npm run m0:cancel -- dsh-account
```

Codex 基本实验默认查找本机 npm 全局安装的 `codex.js`，位置不同时可按 README 设置 `AGENT_GUILD_CODEX_JS`；停止实验目前仍使用默认位置，尚未统一配置。DSH 实验引用接收方 `~/.dsh/.credentials.yaml`，不存在该文件或认证不可用时，需要在官方本地设置中配置，不能使用包里不存在的“作者密钥”。

## 10. 已知技术限制与交付边界

- DSH Runtime 固定为 `0.2.2-rc.1`，官方客户端固定为 `0.0.1-rc.1`，两者公开能力不完全同步。基本实验使用官方客户端；交互适配使用官方 SDK stdio 协议，没有修改 Runtime 或另造 Agent 引擎。
- 官方客户端的第三方类型声明缺失部分引用，当前启用 `skipLibCheck`；自有源码仍为 strict。类型检查通过不代表第三方声明全部无误。
- 先前依赖审计记录为 209 个受影响依赖项（high 198、moderate 11，含传递影响），不是 209 个独立漏洞编号；本次打包没有升级依赖或重跑审计。进入正式分发前仍需解决依赖与版本兼容问题，不要直接 `npm audit fix --force` 改坏复现基础。
- 目前状态与事件保存在实验内存及 JSON 文件中；数据库持久化、容量控制、正式事件合同和崩溃恢复尚未实现。
- Job Object 是进程生命周期管理，不是安全沙箱；现有实验的文件范围检查也不是完整的产品级资源锁。
- 包内保留历史计划、源码与测试，没有桌面安装器、编译好的 JobHost 或完整运行证据。接收方可依据锁文件安装依赖、重新运行验证；无需复制原作者本机 AppData。

后续按近阶段推进：补齐 M0 → 实现 M1 最小协作核心 → 接入 M2 最小桌面界面。请在修改说明中明确“本次实现了什么、哪些仍是 mock、怎么验证”，便于双方继续统一进度。
